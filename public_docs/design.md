# Graphify の graph.json だけを唯一の保存先にする設計だけでは、出来ない。pgvectorとの併用が必要。

## 動画設計
| 優先 | 機能 | 最初に決めること |
|---|---|---|
| 1 | **ノードの種類** | `動画`、`分析`、`概念`、`設計判断`、`実装`などを区別する。同じ YouTube 動画を何度分析しても動画ノードは一つにする |
| 2 | **エッジの意味と向き** | `分析から抽出した`、`根拠となる`、`実装する`、`前提となる`など、使える関係名を定義する |
| 3 | **根拠への逆引き** | 各知識から元動画、分析の版、会話メッセージへ戻れるようにする。可能なら動画の該当時刻も記録する |
| 4 | **候補と確定の区別** | AI が提案したノード・エッジを即座に確定せず、`候補 → 確認済み → 廃止`で管理する |
| 5 | **変更履歴** | 要約や関係を修正した人・日時・理由を残す。再分析時に古い判断を上書きしない |
| 6 | **重複の整理** | 「画像品質確認」と「入力画像の品質検査」が同じ概念か、人が確認して統合できるようにする |

## Laravel の業務データと Graphify の生成グラフは役割を分ける
| 役割 | 保存先 |
|---|---|
| YouTube ID、動画情報、要約、分析結果、会話との対応 | Laravel のデータベース |
| それらから抽出した概念やコードとのつながりを探索 | Graphify |
| 「このノードとエッジは確定済み」「循環を禁止する」という規則 | Laravel 側の知識テーブルと登録処理 |

## 必要環境
| 部分 | 推奨 | 役割 |
|---|---|---|
| 開発端末 | Windows 11、VS Code、WSL2 Ubuntu、Docker Desktop | 編集とローカル実行 |
| Web アプリ | Laravel 13、PHP 8.3、Livewire スターターキット | 動画登録、分析結果、会話、知識の管理画面 |
| 主データベース | PostgreSQL＋pgvector | 業務データ、ノード・エッジ、必要になれば類似検索 |
| 非同期処理 | Laravel Queue のワーカー | 時間のかかる分析や動画生成ジョブ |
| グラフ探索 | Graphify（WSL2 側で実行） | 文書・コード・動画由来の知識を横断して調べる |
| 動画制作 | Remotion（Node.js／TypeScript） | テンプレートに沿った動画の組み立て |
| AI 動画生成 | Runway API | 必要な場面だけ生成を依頼 |

「モデル使用量」には異なる二種類があります。
| 見たいもの | 表示場所 | 指標 |
|---|---|---|
| **開発中の Codex,Claude,Gemini 使用量** | Codex,Claude,Gemini の公式 usage dashboard、CLI の `/status` | 利用枠と残量 |

動画ファイルそのものは、通常 videos テーブルに入れません。テーブルには YouTube ID や、制作した動画の保存先を記録します。YouTube 動画、Runway の生成物、Remotion の完成品は区別できるよう、たとえば videos.source_type を youtube・runway・remotion とするか、制作物用の別テーブルを設けます。
Livewire で作る画面
最初の開発範囲は、次の四画面が適切です。
1. 動画一覧・登録：YouTube URL を登録し、動画 ID で重複を防ぐ。
2. 動画詳細：要約、分析履歴、関連ノードを表示する。
3. 分析画面：分析をジョブに投入し、進捗と結果を表示する。
4. 知識画面：提案されたノード・エッジを確認し、採用・修正する。
Graphify はこのデータから出力した文書とアプリのコードを解析し、graph.json や閲覧用 HTML を生成できます。公式資料には YouTube URL の追加もあります。ただし、Graphify が生成したグラフの更新と、あなたが確定した知識の保存は別の処理として扱う設計を提案します。Graphify の出力を再生成しても、採用済みのノードとエッジを失わないためです。github.com
構築順は ① Laravel＋Livewire＋PostgreSQL → ② 動画・分析テーブル → ③ AI 会話 → ④ 知識ノードとエッジ → ⑤ Graphify 連携 → ⑥ pgvector 検索 がよいと思います。pgvector は将来使う前提で環境に入れつつ、類似検索が必要になるまでは検索機能の実装を後回しにできます。

Laravel 13＋PostgreSQL を知識の中心にするなら、**最初に決めるべきなのはグラフの見た目より、「何を知識として確定し、どう根拠へ戻れるか」**です。Livewire の画面はそのルールを使って作れます。
画面は「一点から周囲を見る」形にする
最初から全ノードを一画面に描くと、増えたときに読みにくくなります。Livewire では、まず動画や概念の詳細画面を作り、そこに以下を表示するのが実用的です。
- 中央：選んだノードの説明と状態
- 左側：その知識の根拠となった動画・分析・会話
- 右側：関連概念、設計判断、実装
- 操作：関係の追加、候補の採用、誤った関係の修正、元データへの移動
例えば「入力画像の品質確認」を開くと、どの動画・分析から着想し、Runway の失敗防止機能のどこに実装したかが見える状態です。これが今回の目的に合った「ナレッジ表現」だと思います。全体グラフ表示は、その詳細画面が役立つことを確認してから追加できます。
検索は、最初にタイトル・種類・関係・出典で探せるようにします。概念が増えて言い換え検索が必要になったら pgvector を加えます。pgvector は類似候補を探す手段で、二つの概念が同一か、エッジが正しいかの確定は行いません。GitHub
最初の完成目標を一つに絞るなら、「YouTube 動画を登録 → 分析 → 概念と関係を候補として表示 → 人が採用 → 概念画面から元動画と実装へ戻る」です。この一連の操作ができれば、Obsidian に求めていた知識の蓄積方法を Laravel 上で具体的に検証できます。

VideoManager では、ソースコードのグラフと動画から得た知識のグラフを、初期設計から接続できるようにしておくべきです。ただし、保存先ごとの役割を明確にします。
対象	正本	グラフ解析・表示
Laravel・Livewire・Remotion のソース	GitHub／Git	CodeGraph または Graphify
動画、要約、概念、確定したエッジ	PostgreSQL	VideoManager の Livewire 画面
コードと知識の対応	PostgreSQL の対応テーブル	両グラフを横断する画面
CodeGraph の SQLite／Graphify の JSON	ソースから作り直せる解析結果	開発エージェントの検索に利用
