# 仕組みを作る（目標から仕組みを設計する）

利用者が**目標（goal）**や質問を渡し、Gemini（Laravel AI SDK）がその目標を実現する**仕組み**を設計する。
仕組みとは、目標を達成するための「入力 → 処理の手順 → 判断 → 出力」の組み立てと、それを動かすプログラムの案のこと。

最初に決めるべきなのは、AI に何を書かせるかより、**「AI が知らないことを勝手に埋めない」**こと。
足りない情報は、AI が想像で補わず、**候補を 2〜3 個出すか、利用者に質問して確かめる**。知識グラフの「候補 → 確認済み」と同じ考え方を、仕組みの設計にも当てはめる（design.md）。

## 入口

| 場所 | 内容 | 状況 |
|---|---|---|
| 制作一覧（`/productions`）の見出しの右 | 「制作を作る」の横に「**仕組みを作る**」ボタンを置く。押すと `/mechanisms/create` へ。「仕組みの一覧」へのリンクも置く | 済み |
| 仕組みを作る（`/mechanisms/create`） | 目標（10〜4000 文字）と名前（任意。空なら目標の 1 行目の先頭 40 文字）を入力し、仕組みと 1 周目（① 目標の理解・待機中）を作る（`CreateMechanism`） | 済み |
| 仕組みの一覧（`/mechanisms`） | 作った仕組み、目標、今の段階、何周目か、状態。本人の仕組みだけ | 済み |
| 仕組みの詳細（`/mechanisms/{mechanism}`） | ループの各段階の結果、質問への回答欄、結果報告、「まだ回すか」の確認。本人以外は 404 | ① 目標の理解・⑥ 結果報告の表示、失敗時の「この段階からやり直す」、「まだ回す：いいえ（完了）」は済み。② 知識検索の表示、「はい」（次の周への入力）、前の周の表示も済み |

メニューは増やさず、制作の下に置く（仕組みは、制作と同じく知識から何かを作る作業のため）。仕組みが増えて制作と並べにくくなったら、メニューを分ける。

## ループ

```
目標（goal）を入力
  ↓
① 目標の理解        目標を言い換え、達成したと言える条件（完了条件）を書く
  ↓
② 知識検索          プロジェクト内の知識（確認済みの概念・設計判断・実装）を探す
  │                 └ 足りないと判断したときだけ Web を検索する（②-W）
  ↓
③ 前提条件の確認    前提条件・不足情報・判断点を、根拠つきで並べる
  ↓
④ 質問か候補確認    不足情報・判断点ごとに、質問するか、候補を 2〜3 個出す
  │                 ← 利用者が答える・選ぶ（答えるまで ⑤ へ進まない）
  ↓
⑤ 仕組みのプログラム作成   手順・判断・ループ条件と、プログラムの案を作る
  ↓
⑥ 結果報告          何を作ったか、何を根拠にしたか、残った不足情報
  ↓
「まだ回しますか？」 yes → 次の周への入力を書いて ① へ（目標はそのまま、前の周の回答と結果を引き継ぐ）
                     no  → 完了
```

### 各段階の入力と出力

| 段階 | AI に渡すもの | AI が返すもの（構造化出力） | 人の操作 |
|---|---|---|---|
| ① 目標の理解 | 目標、前の周の結果報告と回答（2 周目以降） | `restated_goal`（言い換え）、`done_criteria`（完了条件 1〜5 個）、`scope_out`（扱わないこと） | 言い換えが違えば目標を直す |
| ② 知識検索 | ① の結果、検索で見つかった知識（下の「知識検索」） | `used_nodes`（使う知識の id と理由）、`enough`（知識だけで足りるか）、`web_queries`（足りないときの検索語 1〜3 個）、`why_not_enough` | — |
| ②-W Web 検索 | `web_queries`、① の結果 | `findings`（要点、URL、ページ名） | — |
| ③ 前提条件の確認 | ①②の結果 | `premises`・`missing`・`decisions`（下の「前提条件・不足情報・判断点」） | — |
| ④ 質問か候補確認 | ③ の `missing`・`decisions` | 各項目に `question`、または `candidates`（2〜3 個。それぞれ内容・利点・注意点）と `recommended` | 回答する、候補を選ぶ、「その他」で書く |
| ⑤ 仕組みのプログラム作成 | ①〜④ の結果（回答を含む） | `steps`・`decision_points`・`loop`・`program`（下の「仕組みの形」） | — |
| ⑥ 結果報告 | ⑤ の結果、使った根拠 | `summary`、`criteria_check`（完了条件ごとに満たす／満たさない／未確認）、`remaining_missing`、`next_suggestion` | 「まだ回すか」を選ぶ |

段階ごとに AI を 1 回ずつ呼ぶ（まとめて 1 回にしない）。段階の結果を DB に残し、どこで何を判断したかを後から確かめられるようにするため。また、④ で人が答えるまで止める必要がある。

## 勝手に想像しない決まり

AI への指示（instructions）に必ず入れ、構造化出力でも守らせる。

1. **前提条件には根拠を付ける。** 根拠は `knowledge`（知識ノードの id）・`web`（URL）・`user`（利用者の回答・目標の文）のどれか。根拠を示せない前提は、前提ではなく**不足情報**として返す。
2. **不足情報は埋めない。** 次のどちらかにする。
   - 答えが利用者にしか分からないもの（予算、対象者、締め切り、好み）→ **質問**する。
   - いくつかの一般的なやり方から選べるもの（使うライブラリ、保存先、処理の順番）→ **候補を 2〜3 個**出し、勧める案と理由を付ける。
3. **候補は 2〜3 個に限る。** 1 個では選べず、4 個以上では比べにくい。
4. **確かでないことは、確かでないと書く。** Web の情報は日付とページ名を添え、知識の状態が「候補」なら、人が確認していない知識だと書く。
5. **利用者の回答を上書きしない。** 前の周の回答は、次の周の「確定した前提（根拠 `user`）」として渡す。変えたほうがよいと AI が考えたときは、判断点として出し直す。

処理側でも確かめる：`premises` の根拠の id が渡した知識にない、URL が ②-W の結果にない、候補が 2〜3 個でない、のどれかなら、その段階をやり直す（最大 2 回。それでも駄目なら失敗として表示する）。

## 前提条件・不足情報・判断点

③ で返すもの。どれも `mechanism_findings` に 1 行ずつ残す。

| 種類 | 意味 | 例（目標「YouTube の料理動画から買い物リストを作る仕組み」） |
|---|---|---|
| 前提条件（premise） | 根拠があり、確かだと言えること | 動画の分析は Gemini が URL のまま見られる（根拠：知識「動画の分析」） |
| 不足情報（missing） | 仕組みを作るのに必要だが、まだ分からないこと | 何人分の量にするか（→ 質問） |
| 判断点（decision） | やり方が複数あり、選ぶ必要があること | 材料の名前のそろえ方：A 辞書で変換 / B AI に任せる / C 人が直す（→ 候補） |

## 知識検索

**まずプロジェクト内の知識で考え、足りないと AI が判断したときだけ Web を検索する。**

| 順 | 探すもの | 使うもの | 状況 |
|---|---|---|---|
| 1 | 概念・設計判断・実装 | `KnowledgeSearch`（キーワードと意味の RRF）。検索語ごとに 20 件探し、各一覧での順位を合わせて（RRF）30 件まで AI に渡す。本人が見られる知識だけ（`visibleTo`）。廃止・統合済み・動画・分析のノードは入れない（`MechanismKnowledge`） | 済み |
| 2 | 実装のコードの場所 | `knowledge_code_links`（実装ノードにつながるファイル・メソッド）を、知識の一覧に添えて AI に渡す | 済み |
| 3 | 候補の知識 | 確認済みと同じ検索で一緒に探し、状態を添えて渡す。使うときは「人がまだ確認していない」と理由に書かせる | 済み（足りないときだけ探す形にはしていない） |
| 4 | Web | ② で `enough = false` のときだけ。理由（`why_not_enough`）と検索語を画面に出してから検索する | 未 |

- 検索語は、① で AI が出す検索語（`search_keywords`。2〜10 文字ほどの名詞を 1〜5 個）、① の言い換え、この周への入力、目標の順。短い検索語は名称・説明・出典の一致で、長い文は意味の近さで見つける（design.md の「検索」）。埋め込みを使わない設定・作れなかったときは、キーワードの一致だけで探す。
- ② の AI（`MechanismResearcher`）は、渡した一覧から使う知識（最大 10 件）と理由、知識だけで足りるか（`enough`）、足りない理由と Web の検索語（最大 3 個）を返す。一覧にない id は捨てる。使う知識は `mechanism_sources`（`source_type = knowledge`）に、名称・説明・理由を写して残す（知識が後で変わっても、その周で何を根拠にしたかが分かるように）。やり直したときは、その周の知識の根拠を消してから作り直す。
- 2026-11-10、本物の Gemini で確かめた（目標「動画の分析結果から解説動画の台本を自動で作る」）。意味の近さで 30 件見つかったが、類似度 0.6〜0.73 の、動画の分析から作った概念がほとんどで、関係の薄いもの（「高強度インターバルトレーニング」0.62 など）も入った。AI は 1 件だけを選び、足りないと判断して Web の検索語を 2〜3 個出した。2 周目の入力「既存の制作（台本の候補）の仕組みを使えるか」には、関係する実装ノードがない（台本の候補を作るコード `GeminiScriptWriter` を指す実装の知識がない）ため、何も選ばなかった。プロジェクト内の仕組みを使わせるには、実装ノードとコードの対応（`knowledge_code_links`）を増やす必要がある。
- Web 検索は SDK の `Laravel\Ai\Providers\Tools\WebSearch`（Gemini では Google 検索）を使う。検索の回数は `max(3)` に抑える。
- Web の結果は、仕組みの根拠（`mechanism_sources`）に URL・ページ名・要点・取得日時を残す。知識には自動で入れない。役に立ったページは、詳細画面から「情報源に登録」して、いつもの分析の流れ（web_sources.md）に乗せる。
- 個人のファイルから作った知識は、本人の仕組みでだけ使う。Web 検索の検索語に個人のデータを入れない（指示で禁止し、検索語を画面に出して確かめられるようにする）。

## 仕組みの形（⑤ の出力）

| 項目 | 内容 |
|---|---|
| `steps` | 処理の手順。各手順に、入力・処理・出力・使う既存のクラス（あれば） |
| `decision_points` | 処理の途中の判断。条件と、それぞれの分かれ先 |
| `loop` | 繰り返しの条件。何を繰り返すか、続ける条件、止める条件、最大回数 |
| `missing_handling` | 処理中に情報が足りないとき、どこで誰に聞くか（仕組み自体にも「勝手に想像しない」を入れる） |
| `program` | プログラムの案。ファイルのパス、言語、コード（Laravel のクラス、Artisan コマンド、ジョブなど） |
| `tests` | 動いたと言える確かめ方（Pest のテストの案、手で確かめる手順） |

### プログラムは案として残し、自動では反映しない

`program` は `mechanism_rounds.program` に保存し、詳細画面でコードとして表示するだけにする。リポジトリのファイルには書き込まない。

- 画面から AI にコードを書き込ませると、検証されないまま動いてしまう。既存の `CodeFixer`・`CodeChangeApplier` は tree-sitter で構文を確かめるが、意味が正しいかまでは分からない。
- 反映は、開発者が Claude Code・Codex で案を読んで行う。詳細画面に「案を Markdown でコピー」を置く。
- 後で反映を画面から行うなら、`CodeChangeApplier` を使い、人が差分を見て承認してから書き込む（判断点 1）。

## まだ回すか

⑥ の後に「まだ回しますか？（はい／いいえ）」を出す。

| 選択 | 動き |
|---|---|
| はい | **はっきりしない点への回答**と**次の周への入力**を書いて、次の周を作り、① から始める（済み）。目標は前の周のまま変えずに引き継ぎ、画面にも表示する |
| いいえ | 仕組みを「完了」にする（済み）。完了した仕組みは「再開する」で「まだ回しますか？」に戻せる（済み） |

- はっきりしない点は、結果報告の「まだ足りない情報」（なければ ① の「はっきりしない点」）を 1 つずつ並べ、それぞれに回答欄を付ける（`MechanismLoop::openQuestions`）。分からない・決めていない項目は空のままでよく、次の周でもはっきりしない点として残る。回答か次の周への入力の、どちらか 1 つは必要。
- 回答は、質問が出た周の `mechanism_findings`（`kind = missing`、`question`・`answer`・`answered_at`）に残す。次の周の AI には `answers`（利用者が確定した前提）として渡し、上書きさせない。② の検索語にも使う。④ 質問か候補確認ができたら、ここに候補（2〜3 個）からの選択も加える。
- 次の周への入力（任意）は `mechanism_rounds.instruction` に残す。

- 次の周の AI には、目標・この周への入力・前の周の要点（`previous_rounds`：入力、言い換え、完了条件、使った知識、結果報告）を毎回渡す。① は入力を反映して言い換え・完了条件を作り直し、入力と目標が食い違うときは入力を優先して、はっきりしない点で確かめる。② は入力も検索語に使う。
- 詳細画面では、今の周を開いて表示し、前の周は閉じて（`details`）結果報告の要約だけを見せる。入力欄の例文には、前の周の「次の周でするとよいこと」を出す。

- 止める条件は人が決める。AI は `criteria_check` で完了条件を満たしたかを報告するだけで、勝手に終わらせない。
- 周の上限は 5 周（`Mechanism::MAX_ROUNDS`）。超えるときは目標を分けることを勧める（AI の費用と、会話が長くなりすぎるのを防ぐため）。
- 同じ周の中では、④ で回答がそろうまで ⑤ へ進まない。「分からない」と答えた項目は、AI が勧める候補を仮に採用し、結果報告で「仮の前提」として必ず挙げる。

## 画面（仕組みの詳細）

```
┌ 仕組み：料理動画から買い物リストを作る ───────────── 2 周目 / ④ 回答待ち ┐
│ 目標：……                                                             │
│ ① 言い換え・完了条件      ② 使った知識（3）・Web（2）  [根拠を見る]    │
│ ③ 前提条件 4 / 不足情報 2 / 判断点 1                                   │
│ ④ 確認してください                                                    │
│   Q1 何人分の量にしますか？          [ 2 人分        ]                 │
│   D1 材料の名前のそろえ方            ( ) A 辞書で変換（おすすめ）      │
│                                      ( ) B AI に任せる                 │
│                                      ( ) C 人が直す   ( ) その他 [  ] │
│                                                       [回答して進む]   │
│ ⑤ 仕組み・プログラムの案   ⑥ 結果報告                                 │
│                                      [まだ回す：はい] [いいえ（完了）] │
└────────────────────────────────────────────────────────┘
```

- 各段階はキューのジョブで動かし、画面は `wire:poll` で進み具合を見る（分析・台本の候補と同じ）。
- 段階ごとに「この段階からやり直す」を置く。

## AI の構成（Laravel AI SDK）

| クラス | 役割 |
|---|---|
| `App\Ai\Agents\MechanismDesigner` | ①③④⑤⑥ を担当。段階ごとに instructions と schema を切り替える（コンストラクタで段階を受け取る）。`HasStructuredOutput`。今は ① と ⑥ だけ（済み）。前の段階の結果は会話の履歴ではなく入力の JSON で毎回渡す。周をまたいで会話を続ける（`Conversational`＋`RemembersConversations`）かは構築順 ⑦ で決める |
| `App\Ai\Agents\MechanismResearcher` | ② と ②-W。②は知識の一覧を渡して `enough` を判断させる（済み）。②-W は `tools()` に `WebSearch` だけを持つ（未） |
| `App\Services\Mechanisms\MechanismLoop` | 段階を順に進め、次の段階のジョブを入れる。④ で止め、回答がそろったら ⑤ へ。今は ① → ⑥ → 「まだ回すか」（済み）。② 〜 ⑤ は飛ばし、結果報告で「行っていない」と AI に伝える。AI の出力は保存前に整える（重複・空の項目を除く、件数の上限、完了条件は ① の項目に合わせ、決まった値でない判定は「未確認」） |
| `App\Services\Mechanisms\MechanismKnowledge` | 知識検索（`KnowledgeSearch`、`visibleTo`）と、AI に渡す知識の一覧を作る（済み）。前の周の要点は `MechanismLoop` が入力に入れる |
| `App\Services\Mechanisms\FindingValidator` | 「勝手に想像しない決まり」の処理側の確認 |
| `App\Jobs\RunMechanismPhase` | 1 段階を動かすジョブ（タイムアウト 300 秒、自動ではやり直さない、失敗は `phase_status = failed`）。周の今の段階でないジョブは何もしない（済み） |

- プロバイダとモデルは `TextAi::fromConfig()` と `GeminiModels::attempt()`（混雑・回数制限のときは次のモデル）。Web 検索は Gemini（または OpenAI）のときだけ使え、使えない設定のときは知識だけで進め、結果報告で「Web は調べていない」と書く。
- AI 使用量は `AiUsageLog` に機能 `mechanism`（`FEATURE_MECHANISM`。呼び出し元は仕組みの周）を足して記録する（済み）。
- 名前を書かずに作ったときは、① で AI が付けた名前（30 文字以内）に置き換える。利用者が書いた名前は変えない。
- 2026-11-10、本物の Gemini で 1 周を確かめた（目標「登録した YouTube の料理動画から、2 人分の買い物リストを自動で作りたい」）。完了条件 3 個・はっきりしない点 3 個が出て、結果報告は仕組みを作っていないことを正しく伝え、完了条件をすべて「未確認」にした。
- 指示に毎回入れる知識の一覧は会話の履歴に入れない（`KnowledgeAssistant` と同じ。履歴が膨らまないように）。

## 知識へ戻す

完了した仕組みは、詳細画面の「設計判断として残す」で、**候補**の設計判断ノードにする（自動では確定しない）。

- 使った知識ノードから、設計判断へ `根拠となる` のエッジ（候補）を引く。出典（`knowledge_sources`）は仕組みの会話のメッセージ。
- 人が知識の画面で確認すれば、既存の「この設計判断から制作を作る」で動画の制作にもつなげられる。

## 決めること（判断点）

| # | 判断点 | 候補 | 勧める案 |
|---|---|---|---|
| 1 | プログラムの案をリポジトリに書き込むか | A 案として表示するだけ / B `CodeChangeApplier` で人が承認して書き込む / C 別ブランチに書き込む | A。動かして役立つと分かってから B を検討 |
| 2 | 構造化出力と Web 検索を同じ呼び出しにするか | A 分ける（②-W は文章で返させ、③ で構造化）/ B 同じ呼び出しにする | A。Gemini のモデルによっては、ツールと構造化出力を同時に使えない |
| 3 | 仕組みを利用者ごとに分けるか | A 本人だけ（`owner_id`）/ B 全員で共有 | A。個人の知識を使うことがあるため。共有は「設計判断として残す」で行う |
| 4 | 置き場所 | A 制作の下（`/mechanisms`、メニューは制作）/ B 独立したメニュー | A。数が増えたら B |

## 構築順

① テーブルとモデル、「仕組みを作る」ボタンと作成画面（済み）→ ② ① 目標の理解と ⑥ 結果報告だけの 1 周（知識なし。済み）→ ③ 知識検索（済み）→ ④ 前提条件・質問・候補と回答画面（`FindingValidator`）→ ⑤ プログラムの案 → ⑥ Web 検索 → ⑦ 「まだ回す」と周の引き継ぎ（次の周への入力と前の周の要点の引き継ぎは ③ と一緒に済み。会話の履歴で続けるかは未定）→ ⑧ 設計判断として残す

各段階でテストは `Laravel\Ai` のフェイク（`MechanismDesigner::fake()`）を使い、Gemini を呼ばない。
